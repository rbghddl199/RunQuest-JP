# RunQuest 想定質疑応答

発表・デモの際に受ける可能性が高い質問を、機能・データ・パフォーマンス・技術選定・限界の観点から整理しました。

## プロジェクト概要

### 1. RunQuest はどのような課題を解決するサービスですか?

RunQuest は、ランナーが自分の体調・好み・位置・過去記録をもとに、今日走るのに適したコースを簡単に見つけられるようにするサービスです。単なるコース一覧ではなく、アンケート・ランニング記録・現在地・天気情報を組み合わせて次の行動を推薦します。

### 2. 既存のランニングアプリとの違いは何ですか?

一般的なランニングアプリは記録保存と統計表示に重点を置いていることが多いです。RunQuest は記録保存に加えて、コース推薦、GPX ベースのコース管理、コミュニティ投稿との連携、チャットボット推薦、バッジや出席による動機付けまでを一体的に提供します。

### 3. なぜ大田(テジョン)地域を中心に実装したのですか?

デモと検証が可能な範囲を明確にするため、大田地域に限定しました。コース座標や GPX データを直接検証でき、Kakao Map 上で実際の経路が正しく表示されるかを確認しやすいためです。

### 4. ユーザーはどのような流れでサービスを利用しますか?

ユーザーは会員登録後にアンケートを完了し、推薦コースを確認します。コースを選択して GPS またはシミュレーションモードでランニングを開始し、終了後に記録とフィードバックを確認します。自由ランニングで作成した経路は自分のコースとして保存し、その後の投稿作成にも連携できます。

## 推薦機能

### 5. コース推薦はどのような基準で動作しますか?

推薦はアンケートスコア、直近のランニング記録、現在地、復帰ユーザーかどうか、安全補正値を組み合わせて計算します。位置情報の権限がある場合はコース起点との距離を大きく反映し、記録が蓄積されるほどユーザーの実際のランニング傾向の比重を高めます。

### 6. 新規ユーザーと既存ユーザーで推薦方式はどう違いますか?

新規ユーザーは記録が不足しているため、アンケート結果を中心に推薦します。既存ユーザーは直近記録の距離・ペース・好みのコースタイプも併せて反映します。長期間記録のない復帰ユーザーには、無理のないコースを優先するよう安全補正の比重を置いています。

### 7. 推薦アルゴリズムは AI と言えますか?

コアとなるコースのランキングは、説明可能なルールベースのスコアリング方式です。生成AIはチャットボット応答、推薦理由の説明文、ランニングフィードバック文の生成に補助的に使用しています。外部 AI 呼び出しが失敗しても、ローカル fallback によってサービスフローは維持されます。

## ランニング機能

### 8. GPS ランニングとシミュレーションランニングはどう違いますか?

GPS ランニングはブラウザの `navigator.geolocation.watchPosition` で実際の位置を追跡します。シミュレーションランニングは選択したコースのルートポイントを時間経過に応じて補間しながら移動する方式です。シミュレーションはデモ用で、実際の位置情報権限がなくてもフローを見せられるようにするために使用しています。

### 9. GPS がオフ、または権限がない場合はどうなりますか?

GPS 権限がない場合、リアルタイム位置追跡は動作しません。ユーザーはシミュレーションモードでランニングフローを確認できます。実際のデプロイ環境では、GPS は HTTPS のセキュアコンテキストでのみ安定して動作するため、HTTPS でのデプロイが必要です。

### 10. 一定距離未満の記録を保存しないのはなぜですか?

誤って開始してすぐに終了した記録や、GPS 誤差による無意味な記録を防ぐため、最低 100m 以上移動したランニングのみを保存するようにしています。基準未満の場合は記録を削除し、ユーザーに案内します。

### 11. 自由ランニング完了後にコースとして保存できますか?

可能です。デフォルトの DB コースではなく自由ランニングでトラックポイントが十分に蓄積された場合、完了ページでその経路をユーザーコースとして保存できます。保存したコースはマイコース一覧やコミュニティ投稿作成のフローに連携されます。

## データと DB

### 12. 主要なエンティティは何ですか?

主要エンティティはユーザー、プロフィール、設定、アンケート回答、基本コース、ユーザーコース、ランニング記録、出席、バッジ、通知、コミュニティ投稿、コメント、いいね、保存済み投稿、チャットボットセッション、推薦セッションです。詳細な関係は `docs/ERD.md` にまとめています。

### 13. GPX ベースのコースデータはどのように作成しましたか?

ユーザーから提供された GPX ファイルを解析し、ルートポイント、距離、獲得標高、開始座標を計算しました。経路情報のない既存コースは削除し、検証可能な GPX コースのみを fixture と DB に反映しました。

### 14. コース削除時に既存の記録や投稿はどう保護されますか?

コースに紐づくランニング記録・投稿は `SET_NULL` ポリシーを使用しています。そのためコースが削除されても記録や投稿自体は消えず、紐づくコースの値だけが空になります。

### 15. 0km のランニング記録を削除したのはなぜですか?

0km の記録は実際のランニング成果や推薦アルゴリズムを歪める可能性があります。統計・出席・推薦の重みづけがより正確になるよう既存の 0km 記録を整理し、新しい記録も最低距離条件を満たさなければ保存されないようにしました。

## コミュニティとパフォーマンス

### 16. コミュニティ一覧が遅かった原因は何ですか?

一覧レスポンスに詳細コース、ランニング記録、コメント、base64 画像のような重いデータが含まれていました。そのためレスポンスサイズとクエリ数が不必要に大きくなっていました。

### 17. どのようにコミュニティページを最適化しましたか?

一覧 API では画像原本と詳細な nested データを除外し、いいね数・コメント数は annotation で計算するようにしました。`select_related`、`prefetch_related`、`defer`、DB インデックスを適用し、一覧 API をほぼ 1 クエリ水準まで削減しました。

### 18. パフォーマンスログはどのように確認しますか?

`.env` に `RUNQUEST_PERFORMANCE_LOGS=True` を設定すると、リクエストごとの実行時間とクエリ数が `backend/runquest-performance.log` に記録されます。関数単位の計測は `time_block` ユーティリティで記録します。

### 19. 現在の計測結果はどうなっていますか?

ローカル DB 基準で、コミュニティ最新一覧は約200ms/1クエリ、人気一覧は約15ms/1クエリ、詳細取得は約11ms/2クエリ程度です。チャットボットのローカル応答は約31ms程度です。

## 技術選定

### 20. なぜ Django REST Framework と Vue を採用したのですか?

DRF は認証・シリアライズ・権限・API ドキュメント化に強みがあり、Vue は SPA の画面構成と状態管理が軽量です。バックエンドとフロントエンドを明確に分離し、REST API ベースの構成を作るのに適していました。

### 21. Pinia はどのような役割を担っていますか?

Pinia は認証状態、コース、ランニング、推薦、コミュニティ、チャットボット、通知といったフロントエンドの状態を管理します。画面遷移中も必要なデータを保持し、API 呼び出しロジックを分離するために使用しました。

### 22. JWT 認証フローはどのように構成されていますか?

ログイン時に access token と refresh token を発行します。フロントエンドの Axios クライアントが access token を `Authorization` ヘッダーに載せてリクエストし、期限切れ時には refresh token で更新します。

### 23. Kakao Map 連携で注意すべき点は何ですか?

Kakao Map JavaScript SDK のキーが必要で、デプロイ先ドメインを Kakao Developers の Web プラットフォームに登録する必要があります。地図表示座標は緯度/経度の順序と Kakao Map の LatLng 入力順序を混同しないよう注意が必要です。

## 限界と改善方向

### 24. 現在のプロジェクトの最大の限界は何ですか?

実機モバイル GPS での長時間検証がまだ十分ではなく、画像は本番運用向けのファイルストレージ方式ではなく base64 JSON ベースのフローが残っています。またローカル SQLite 基準で最適化されているため、本番規模では PostgreSQL への移行が必要です。

### 25. 画像アップロードはどう改善できますか?

投稿画像の原本を DB の JSON に保存するのではなく、Django media や S3 のようなオブジェクトストレージに保存し、URL のみを DB に保持する方式に変更するのが望ましいです。一覧にはサムネイル URL のみを提供すれば、レスポンスサイズをさらに削減できます。

### 26. 推薦アルゴリズムはどのように高度化できますか?

現在は説明可能なスコアベースの方式です。今後はユーザー行動ログ、コース完走率、ブックマーク、投稿への反応を追加し、パーソナライズの重みづけをより精緻にできます。十分なデータが蓄積されれば、協調フィルタリングや埋め込みベースの推薦も検討できます。

### 27. 本番用 DB へ移行するには何が必要ですか?

PostgreSQL の設定、環境変数の分離、マイグレーション検証、インデックスの再確認、media/static ファイルの処理、HTTPS デプロイ、CORS/Allowed Hosts 設定が必要です。デプロイ後は実際のリクエストログをもとに、遅いクエリを改めて点検する必要があります。
