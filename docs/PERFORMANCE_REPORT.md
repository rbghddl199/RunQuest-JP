# パフォーマンス計測・改善レポート

## 計測方式

RunQuest はリクエスト単位・関数単位で実行時間を計測できるように構成しています。

| 場所 | 役割 |
| --- | --- |
| `backend/core/middleware.py` | API リクエストごとの実行時間と DB クエリ数を記録 |
| `backend/core/performance.py` | 特定のロジックブロックの実行時間を計測 |
| `backend/scripts/analyze_performance.py` | コミュニティとチャットボットの主要 API のパフォーマンスを計測 |
| `backend/runquest-performance.log` | パフォーマンスログの保存ファイル |

パフォーマンスログは `.env` に以下の値を設定すると有効になります。

```env
RUNQUEST_PERFORMANCE_LOGS=True
RUNQUEST_SLOW_REQUEST_MS=350
```

## 直近の計測結果

ローカル SQLite DB 基準の計測結果です。

| 項目 | 結果 |
| --- | ---: |
| コミュニティ最新一覧 | 約202ms / 1クエリ |
| コミュニティ人気一覧 | 約15ms / 1クエリ |
| コミュニティ詳細 | 約11ms / 2クエリ |
| チャットボットのローカル応答 | 約31ms / 16クエリ |

## 適用した改善

1. コミュニティ一覧 API から base64 画像の原本を除外した。
2. 一覧 API から詳細コース・ランニング記録・コメントの nested データを除外した。
3. いいね数・コメント数は serializer での反復クエリではなく、DB annotation で計算するようにした。
4. 投稿・コメント・いいね・保存テーブルに検索用インデックスを追加した。
5. `select_related`、`prefetch_related`、`defer` を適用し、不要なクエリとレスポンスサイズを削減した。
6. チャットボットの応答処理に段階的なログを残し、ボトルネックを確認できるようにした。

## 追加改善の候補

| 候補 | 理由 |
| --- | --- |
| 画像ファイルストレージの変更 | base64 JSON より media URL や S3 URL 方式の方が本番運用に適する |
| コミュニティ人気一覧のキャッシュ化 | いいね/コメント数ベースのソートはデータ増加とともにコストが上がる |
| PostgreSQL への移行 | 本番規模では SQLite よりインデックスと並行処理の面で有利 |
| フロントエンド画像の lazy loading | 初期レンダリングコストの削減 |
| API ページネーションの標準化 | 一覧データの増加に備える |
